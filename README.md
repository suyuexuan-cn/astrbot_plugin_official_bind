# astrbot_plugin_official_bind（v2.4.0 合并版）

> **v2.4.0 新特性：官方回复发送优先级。** 每个群各自维护最近消息的 msg_id 与时间：5 分钟内回复优先用 msg_id 走**被动回复**（不占主动额度），超时/失败改用**主动群消息**，两级都失败再退回非官方 bot。配置项 `passive_reply_window_seconds`（默认 300 秒）可调。

> **v2.3.0 新特性：官方机器人备用入口。** 双 bot 同群时两端收到的同一条用户消息按「群号+发送者+文本」内容对比去重（先到先处理，只跑一次、只回一条）；被 @ 时官方机器人自己处理回复；非官方机器人掉线时官方端自动接管入口，群聊不至于失声。详见下方「官方备用入口」一节。

**QQ 官方机器人 ⇄ OneBot v11 一体化插件**。本插件由原来的两个插件合并而成：

- `astrbot_plugin_official_bind`（身份绑定 / 数据迁移）
- `astrbot_plugin_reply_forward`（同群双 bot 接收去重 / 回复转发）

合并后**只需安装这一个插件**。`data/plugin_data/astrbot_plugin_official_bind/id_mapping.json` 是唯一的数据文件，绑定完成后群映射立即对去重与转发生效（不再有文件缓存延迟）。

> ⚠️ 升级后请**卸载 / 不要再安装** `astrbot_plugin_reply_forward`，否则两个插件会同时注册去重与转发钩子，造成重复拦截。旧的 `id_mapping.json` 可直接沿用，结构未变。

## 一、身份绑定与数据迁移

QQ 官方机器人用 openid / group_openid 标识用户与群，与 OneBot v11 的 QQ 号 / 群号完全不可换算，历史数据无法直接挂到官方机器人上。

```
官方 bot 群/私聊：@官方机器人 /数据迁入
  └─> 得到一段带身份码的说明消息
        └─> 群数据：把消息发到非官方 bot 所在的群
            个人数据：私聊非官方 bot 发送（群聊/私聊均可粘贴）
              └─> 完成绑定，写入 id_mapping.json
```

绑定记录包含显式 id 对应关系：群聊 `qq_group_id ↔ group_openid`，私聊 `qq_user_id ↔ user_openid`，以及两端 umo / session 信息。

### 个人 id 绑定（v2.2）

官方机器人的 openid 是**用户维度、跨群稳定**的：同一个人在任意群（以及私聊）拿到的 openid 都是同一个值。因此个人映射**按 QQ 号全局唯一**，一次绑定全部群生效。

```
群会话绑定完成后，任意成员在官方 bot 群里发 /数据迁入
  └─> 得到「个人身份码」（含该成员 openid）
        └─> 把说明消息发给非官方 bot（群聊或私聊都行）
              └─> 写入 id_mapping.json 的 users 表：QQ 号 ↔ 官方 openid
```

- 按 QQ 号唯一：同一人重复绑定只更新，不重复插记录。
- 不限定粘贴的群：openid 跨群通用，粘到任意群都能正确对应到本人。
- 这样记忆 / 好感度 / 签到等按用户区分的数据才有迁移依据。
- `enable_member_bind` 可关闭此功能（关闭后群绑定过就一律提示已完成）。

**迁移历史数据**：同目录 `migrate_to_official.py` 读取 `id_mapping.json`（或 `/导出映射` 导出的 CSV），把主库 `data_v4.db`、livingmemory 等库里的旧 umo 改写成官方 umo。加 `--user-ids` 用 users 表把消息/记忆记录里的 `sender_id`（QQ 号）改写成官方 openid。默认干跑只统计，`--execute` 才写库，写前自动备份、检测到 WAL 非空（AstrBot 还在跑）会拒绝执行。

## 二、双 bot 同群：内容对比去重 + 回复转发

两个机器人在同一个群时，同一条用户消息会被两个适配器各收到一次 → 管线跑两遍、回复两条。v2.4 改用**内容对比 + 先到先得**：两端消息按「统一群号 + 统一发送者(openid) + 规范化文本」生成指纹，窗口内先到者认领进管线、后到者静默，保证只跑一次、只回一条。

| 环节 | 位置 | 作用 |
|---|---|---|
| 1 | `Platform.commit_event` 包装 | 事件进管线前按内容指纹认领；后到者直接丢弃（早于 WakingCheckStage，不触发权限提示） |
| 2 | `priority=9999` 自定义过滤器 | 补丁未挂上时的兜底，同一套内容对比逻辑 |
| 3 | `bot.send_group_msg` 包装 | gscore_adapter 等绕过管线的协议直发也转官方代发 |

```
任意一端收到群消息（双 bot 已绑定群）
  ├─ 官方专属指令（默认 /数据迁入）？ ──是──> 官方端执行、非官方端让位
  ├─ 非官方端 @官方机器人（At.qq ∈ ignore_sender_ids）？ ──是──> 非官方让位，官方独占处理
  ├─ 自身消息 / 官方代发回声 / 官方 bot UIN ？ ──是──> 静默丢弃
  └─ 其余 ──> 内容指纹先到先得：先到者处理，后到者静默
              · 非官方先到（常态）→ 非官方处理 + 官方代发
              · 只有官方到（非官方掉线）→ 官方端自己接管处理
```

> 由于本地 NapCat 通常比官方 Webhook 快约 1 秒，普通消息多数由非官方端认领、官方端代发；这是正常的，回复账号仍是官方机器人。「官方机器人收到群消息」以 INFO 记录，便于确认官方入口确实收到。

回复转发链路（`@filter.on_decorating_result` 发送前钩子 + 协议端兜底）：

```
非官方 bot 生成群回复
  ├─ 该群没有群绑定 / 官方端未就绪 / 内容不可转发 ──> 原路径发送（不干预）
  └─ 消息链清洗（保留文本/图片/语音，丢弃 @ 与引用，展开合并转发节点）
        └─> context.send_message 官方群 umo
              ├─ 成功 ──> 清空原消息链，官方 bot 已代发
              └─ 失败 ──> 保留原链，非官方 bot 照常发送（绝不丢消息）
```

第三方插件直接调协议 API 时走第 3 层：把 OneBot 消息段还原成消息链（文本/图片/语音，丢弃 @ 与引用），同样转由官方 bot 代发；失败则调用原方法，消息照常从非官方 bot 发出。

**回环防护**：官方 bot 代发的消息会被同群的非官方 bot 再次收到。第 1 层按 `sender_id == self_id` 丢弃自身消息；另有文本指纹窗口（`echo_guard_seconds`，默认 10 秒）。**官方 bot 自己在 NapCat 侧的 UIN 需加入 `ignore_sender_ids`（填你自己的 UIN，插件会从 `@官方bot` 消息自动学习）**，这类消息在管线前就被丢弃——既防止重复处理，也防止官方 bot 发的身份码说明被当成用户粘贴、写出「QQ=官方 bot UIN」的错误绑定。插件还会从「非官方端 @官方bot 发 `/数据迁入`」的 At 组件自动学习新的 UIN；换官方 bot 时可在配置里追加。升级时会自动清理历史误绑记录（日志提示 `已清理 N 条把官方 bot 误当用户的个人映射`），之后用真实 QQ 号重新粘贴身份码即可。

**平台 id 自动迁移**：同一套 appid 可配成 `qq_official_webhook` 或 `qq_official`。在 WebUI 里切换适配器后平台 id 会变（例如 `default` → `QQBOT-websocket`），旧绑定会指向不存在的平台。v2.1 在启动 / 平台加载时自动把 `new_umo` 的平台段换成当前实际运行的官方平台 id 并落盘，无需重新绑定。

**数据文件结构（v2.2.2）**：`id_mapping.json` 顶层分成两个区块，群聊和个人彻底分开：

```json
{
  "salt": "...",
  "groups": { "pending": {}, "bound": [] },
  "members": { "pending": {}, "users": [] }
}
```

- `groups`：群聊会话身份码 + 群号↔群openid 绑定。
- `members`：个人身份码 + QQ号↔个人openid 映射。
- 旧版四段式（`pending`/`bound`/`users` 平铺）启动时自动迁移成上面的结构；迁移时**只保留群聊绑定**，个人映射与个人身份码一律丢弃，群记录里被误写成官方 bot UIN 的发起人会按 user_openid 反查正确 QQ 号后纠正（反查不到则原样保留，不会瞎改）。迁移脚本 `migrate_to_official.py` 同时兼容新旧格式。

## 前提条件

1. 官方机器人开通**群聊主动消息权限**（否则官方端无法主动推送回复/绑定通知）。
2. 官方端「就绪」：AstrBot 启动后官方 bot 至少收到过该群的一条消息（被 @ 一次即可）。未就绪期间全部退回原路径，不会丢消息。
3. 在双 bot 群完成**群绑定**后，去重与转发才会对该群生效（依据是 `id_mapping.json` 里 `scope=group` 的记录）。

## 指令

| 指令 | 权限 | 说明 |
|---|---|---|
| `/数据迁入` | 全部（可设仅管理员） | 官方 bot 上生成身份码（群首次=群码，群已绑定=个人码） |
| `/绑定列表` | 管理员 | 查看待绑定 / 会话绑定 / 个人映射 |
| `/解绑 <码或QQ号或umo片段>` | 管理员 | 删除绑定、个人映射或撤销待绑定码 |
| `/导出映射` | 管理员 | 导出映射 CSV + 个人映射 `user_mapping_*.csv` |
| `/转发状态` | 管理员 | 查看群映射、官方端就绪状态、去重配置与统计 |

## 三、官方机器人备用入口（v2.3.0）

原来官方机器人只做「回复出口」：在已绑定的双 bot 群里，它的普通群消息（含 @它）在进管线前就被丢弃，导致 @官方机器人没有反应、非官方机器人一旦掉线群里就没人回复。

v2.3.0 改用**内容对比**：两端同群收到同一条用户消息时，按「统一群号 + 统一发送者(openid) + 规范化文本」生成指纹，先到者认领进管线、后到者丢弃。由此：

- **只处理一次、只回一条**：无论哪端先到，同内容在窗口内只认领一次。
- **@官方机器人**：由官方端认领并自行处理，回复由官方账号发出。
- **非官方掉线**：只剩官方那份消息到达，官方端认领并接管入口，群聊继续可用；不需要主动探测 NapCat 是否在线。
- 官方端**没开「接收全部群消息」**的群收不到普通消息，不会产生事件，完全不受影响；@它的消息（无需全量权限）仍可正常处理。

> 前提：官方机器人需开通**群聊主动消息权限**，否则接管后也发不出（日志会出现「主动消息失败, 无权限」）。

## 注意事项

- 只处理**群聊**，私聊不受影响；官方独占的群（无群绑定）也不受影响。
- 管理指令默认走非官方端执行、官方 bot 代发，两端都能触发且不会重复；若希望某指令在官方端直接执行，加进 `official_only_commands`。
- 官方平台无法呈现 QQ 号 @ 和引用回复，转发时这类组件会被丢弃；纯 At/引用（无正文）的消息直接退回原路径。
- 若开启了 LLM 流式输出，每个分段都会单独走一次发送，第 3 层会逐段代发（与不流式时「一段一条」的表现一致，不会漏到非官方渠道）。
- 官方平台若开启 `use_markdown`，正文里成对的 `_` 会被 QQ 当成斜体标记吞掉（日志里会出现 `officialbind` 这种缺字）。插件的状态文本已避开下划线；自定义文案也尽量不要使用成对下划线。
- 群主动消息有频控（单关系 20 条/分钟、每群每天 1000 条），高频刷屏场景下超限部分可能发送失败并退回。
- 之前在嫙星等插件里配的「群聊忽略平台」可以清空交给本插件统一处理（保留也不冲突，只是重复拦截）。
